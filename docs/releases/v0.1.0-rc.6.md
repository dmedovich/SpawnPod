# SpawnPod v0.1.0-rc.6

Release candidate for coordinated installation upgrades and server validation.

- Add `spawnpod upgrade plan`, `render` and `check`. A deterministic bundle
  coordinates Controller/Agent images, effective configuration, security,
  network, admission and deployment resources, with checksums and inventory.
- Share strict admission comparison between Controller startup and doctor,
  accepting enumerated Kubernetes defaults. Diagnostics identify the failed
  field and spec fingerprints without printing configuration values.
- Check live configuration, managed resource drift, Controller RBAC,
  installation capacity and local image availability on eligible nodes.
  Distinguish temporary Recreate headroom warnings from capacity blockers.
- Add startup and doctor binary/version/configuration fingerprints.
- Document drained upgrades and recovery of the complete previous installation
  in [the upgrade runbook](../UPGRADES.md). Existing render-deployment commands
  now reject differing Controller and Agent images.
- Gate release publication on container upgrade/recovery tests with real
  Forgejo workflows in a disposable K3s installation.

Local Linux/amd64 validation passed `make check`, race tests and two full
container rc.4 → rc.6 preview upgrade/recovery sequences, including intentional
failure, complete rollback, repeated upgrade and eight successful Forgejo jobs.
The release workflow rebuilds and tests the tagged sources before publication.
See [validation details](../VALIDATION.md).

## Before testing on a server

Use the rc.6 CLI and immutable runtime reference from this release's
`GHCR_DIGEST`, plus a separately pinned Runner image. Preserve a complete,
recoverable previous installation before starting. Historical diagnostics
archives are not rollback snapshots.

Follow the runbook's gates: pause submissions, let old jobs finish and clean
up, stop Controller/Runner, apply dependencies and admission, check the switch
gate, then apply deployment/configuration and verify readiness plus a real job.
Do not apply the whole generated directory in one step under a running old
Controller. Keep the existing Runner Secret and environment records.

## Known limits

- The historical rc.5 preflight mismatch has not been conclusively reproduced
  or attributed. New diagnostics and stale-policy tests do not prove its cause.
- Target-server K3s v1.36.4 and ARM64 execution remain to be validated.
- `upgrade apply`, automatic rollback, persistent phase history and
  `upgrade status` are not implemented. Applying and restoring resources use
  explicit operator/GitOps gates with a maintenance interval.
- Admission does not support two active Agent generations during the upgrade.
- Remote image cache checks do not verify registry access, credentials or
  published platform manifests. Verify those before switching.
- One coordinated installation per cluster is supported; namespace and Lease
  migration are outside this upgrade workflow.
